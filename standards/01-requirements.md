# 01 · 需求 / 活 PRD 〔本项目活记忆 · AI 维护〕

> **作用**:这是本项目唯一的需求文档。所有新功能、缺陷、技术债都追加到这里,不要另起多个 PRD 文件。
> **更新时机**:每次有新需求、需求变更、验收标准变化时更新。

---

## 1. 需求来源

| 类型 | 来源 | 进入方式 |
|---|---|---|
| 功能需求 Feature | 用户 / 老师 / 产品 / 客户 | 写成用户故事 |
| 缺陷 Bug | 测试 / 线上日志 / 用户反馈 | 写复现步骤和期望结果 |
| 技术债 Tech Debt | 开发 / Review / CI/CD 故障 | 写影响和修复目标 |

---

## 2. Issue 生命周期

| 阶段 | 状态 | 动作 |
|---|---|---|
| 提出 | Open | 写清场景、目标、验收标准 |
| 排期 | Backlog / Todo | 决定优先级和负责人 |
| 开发 | In Progress | 从 main 开 feature 分支 |
| 评审 | In Review | 提 PR,等待 CI 和 Review |
| 合并 | Done | PR 合并 main,自动关闭 Issue |
| 验收 | Verified | 按验收标准确认 |

**追踪规则**:分支名带 Issue 号,PR 描述写 `closes #<编号>`。

## 4. 需求清单

### US-1 初始化项目工程化与 CI/CD · 状态: Backlog

作为 **项目开发者**,
我想要 项目具备基础工程结构、测试、CI 与 CD,
以便 后续每次开发都能自动检查并自动部署。

验收标准:
- AC1: 从 `main` 开 feature 分支完成初始化,不直接 push main。
- AC2: PR 触发 CI,至少包含格式检查、静态检查、单元测试、覆盖率、`docker build`。
- AC3: CI 全绿后合并 main。
- AC4: 合并 main 自动触发 CD(SSH → 同步 → 构建 → 运行 → 健康检查),健康检查通过。
- AC5: 完成后更新 `standards/PROGRESS.md`。

### US-2 数据分析交互页面 · 状态: Backlog

作为 **银行营销分析人员**,
我想要 在 Web 页面上交互式浏览、筛选、分析营销数据集(分布、分组对比、相关性),
以便 不写代码就能理解客户特征与认购结果之间的关系。

验收标准:
- AC1: Given 应用已启动,When 通过侧边栏进入"数据分析"页,Then 展示数据集概览(行数、列数、`subscribe` 分布)。
- AC2: 页面提供至少 3 类可视化:目标变量分布、单特征分布(分类/数值自动适配)、任意两特征分组对比或相关性热力图。
- AC3: 支持交互筛选(如按 `job`、`marital` 等分类特征过滤),图表随筛选实时更新。
- AC4: 核心统计计算实现为纯函数,单元测试覆盖(正常值/边界值/异常值)。
- AC5: 页面可加载 `data/train.csv` 与 `data/test.csv`,也可切换加载用户上传的同结构 CSV;加载失败给出明确提示不崩溃。

技术备注:
- 分类列含 `unknown` 值(如 `default` 占 21.6%),分析页需明确展示策略(作为独立类别或标注"未知")。
- 图表统一用 Plotly(交互式),配色由 dataviz 规范约束。

### US-3 离线模型训练与评估 · 状态: Backlog

作为 **数据科学家**,
我想要 一个可重复的离线训练脚本,基于训练集训练二分类模型并输出评估报告与模型产物,
以便 在线预测系统能加载模型提供认购预测。

验收标准:
- AC1: Given 训练数据就绪,When 运行训练命令(如 `python -m scripts.train_model`),Then 输出评估报告:准确率、精确率、召回率、F1、AUC,并保存模型产物到 `models/`。
- AC2: 测试集 **AUC ≥ 0.75**,否则脚本以非零退出码失败(作为 CI 门禁)。
- AC3: 固定随机种子,同一数据重复训练输出一致(可复现)。
- AC4: 训练前做 schema 校验,训练/测试列缺失或 `subscribe` 取值异常时给出明确错误。
- AC5: 产物应包含完整预处理流水线(编码、缺失处理),保证训练/预测一致。

技术备注:
- 类别不平衡(正样本 ~13.1%):报告 F1/AUC 而非只看准确率;可评估类别加权或阈值调整,不强制上采样。
- `duration` 是强特征但在真实营销场景预测时未知:训练保留该特征,预测表单不收集,填充策略(如中位数/0)需固定并写入代码注释。

### US-4 在线认购预测 · 状态: Backlog

作为 **银行客户经理**,
我想要 在 Web 页面上通过点选/填写客户信息(下拉框、数字输入)提交后,立即得到该客户是否会认购的预测结果与概率,
以便 快速评估营销名单,优先跟进高概率客户。

验收标准:
- AC1: 预测页所有输入均为点选/填写形式:分类特征用下拉框(选项来自训练数据),数值特征用数字输入框,无需手动输入原文。
- AC2: Given 表单已填写,When 点击"预测"按钮,Then 展示结论(认购/不认购)与认购概率(0–100%),并回显所用关键特征值。
- AC3: 非法输入(如越界数字)给出中文错误提示,页面不崩溃。
- AC4: 预测流水线与训练流水线共用同一预处理,由单元测试验证两者一致性。
- AC5: 模型或数据未就绪时页面给出明确提示,不白屏。
- AC6: `duration` 不出现在预测表单(见 US-3 技术备注)。

技术备注:
- 每个输入项标注取值范围/单位(如 `age` 18–95),降低误填。
- 预测结果旁可附特征重要性最高的几个特征,便于客户经理理解。

### US-5 统一导航与应用入口 · 状态: Backlog

作为 **使用者**,
我想要 单一 Web 入口即可访问数据分析页与预测页,
以便 不用记多个地址。

验收标准:
- AC1: Given 应用启动,When 访问 `http://<host>:<port>/`,Then 进入单一入口,侧边栏含"数据分析"与"认购预测"两个页面,切换无报错。
- AC2: 页面切换不丢状态(数据加载结果带缓存)。

### US-6 Docker 容器化与健康检查 · 状态: Backlog

作为 **运维人员**,
我想要 应用以 Docker 镜像方式运行并暴露健康检查端点,
以便 CI 构建验证与 CD 自动部署。

验收标准:
- AC1: `docker build` 成功;生产镜像仅含运行依赖(开发依赖只在 CI 安装)。
- AC2: 容器内端口固定 8888;启动后 `curl -fsS http://localhost:8888/_stcore/health` 返回 200。
- AC3: Dockerfile 支持 `PIP_INDEX_URL` 构建参数(国内服务器可换镜像源)。
- AC4: 部署脚本幂等可重跑(先 `docker rm -f` 自身旧容器),主机端口 8888 被占用时在 8888~8898 区间自动回退,失败即停。

### US-7 开源仓库与项目文档 · 状态: Backlog

作为 **项目维护者**,
我想要 一个公开仓库与完善的 README(快速开始、本地开发、部署说明、目录结构),
以便 任何人可克隆、复现、参与贡献。

验收标准:
- AC1: 仓库公开于 GitHub(`banksys_sy_lixiaohua`),含 LICENSE(开源协议)。
- AC2: README 含:项目简介、功能截图/说明、本地运行步骤(conda/venv + 依赖安装)、lint/测试命令、Docker 构建与运行、部署后访问地址说明。
- AC3: 代码与文档中无密钥/密码/Token;配置经环境变量 / GitHub Secrets。
- AC4: README 与 `standards/` 保持同步(目录结构变化时更新)。

## 5. 非功能需求

- **安全**:密钥只进 Secrets,不进 Git。
- **可维护**:一需求一小 PR(PR 尽量 < 400 行),避免大爆炸式提交。
- **可测试**:核心逻辑(数据校验、统计、预测构造)必须有单元测试,覆盖率 ≥ 80%。
- **可部署**:部署后必须健康检查通过(`/_stcore/health`);部署脚本 `set -e` 失败即停。
- **性能**:预测响应 < 2s;页面交互无长时间阻塞(数据加载带 `@st.cache_data` 缓存)。
- **可复现**:训练固定随机种子;依赖版本锁在 `requirements*.txt`。
